## 1. Executive Summary

The full 5-step `shotgun-cli` wizard was driven end-to-end inside a tmux
session: help overlay, file selection, template selection + preview modal,
task & rules text input, review, context generation, and clipboard copy. The
core flow is **solid** — context generation succeeded (147 KB output written),
the clipboard was correctly populated, and Unicode/accented/CJK/emoji input
(`codificação`, `ação não`, `中文 café €5 😀`) rendered and round-tripped with
zero dropped characters. Box-drawing and the scrollbar column stayed intact at
60×20, 80×24 and 160×40.

**No blockers and no majors.** Six real issues, all minor or cosmetic: a
glued status/footer line on input screens, a missing "Step 3/5" header on the
Task screen, a confirmation-less `q` quit that can discard typed input, a
silent clipboard copy with no feedback, a fuzzy filter that matches full paths
(burying README.md under cache hashes), and an over-wide progress bar on large
terminals. **Verdict: ship-ready; the six minors are polish items, none block
release.**

## 7. Improvement suggestions (non-bugs)

- **Help is accurate.** The help overlay's step numbering (Template = Step 2,
  Text Input = Steps 3–4, Review = Step 5) matches the live wizard order
  exactly — no drift between docs and runtime. Keep it that way.
- **Filter applies on Enter, not live.** Reasonable for large trees, but a
  live/incremental filter (debounced) would feel more modern; at minimum show
  a match count so the user knows the query did something.
- **`a`/`A` select-all is fast and obvious** — good affordance. Consider a
  visible "N of M visible selected" hint when a filter is active.
- **Quit ergonomics differ by screen** (`q` on nav screens vs `Ctrl+Q` inside
  text inputs). This is correct behaviour, but the footer already documents it
  per-screen — good. Pairs with F-03's confirmation suggestion.

## Findings

### [MINOR] Status line runs into footer hints with no separator on input screens

**Phase:** probe  
**Evidence:** captures/0010-step3-unicode.txt  

On the Task (step 3) and Rules (step 4) screens the status text and the keybinding hint line are concatenated with no space or newline between them. Captured examples: 'Characters: 57Type: Enter text │ Tab: Edit/Done' and '⚠ Task description is required to continueType: Enter text'. The trailing word of the status string is glued to the first word of the hint, which reads as a single broken token and looks like a layout bug.

**Suggested fix:** Render the status/validation line and the hint footer on separate lines (or join with ' │ '). The hint footer is built in task_input.go / rules_input.go View() — emit a newline before the F7/F8 hint block.

---

### [MINOR] Task Input (step 3) is missing the 'Step N/5 • ...' header shown on every other step

**Phase:** probe  
**Evidence:** captures/0009-step3.txt  

Steps 1, 2, 4 and 5 render a header line ('Step 1/5 • Select Files', 'Step 2/5 • Choose Template', 'Step 4/5 • Add Rules & Constraints', 'Step 5/5 • Review & Generate'). The Task Input screen (step 3) renders only the instruction text, with no 'Step 3/5' indicator. internal/ui/screens/task_input.go has no step-title render, unlike the other four screens. Breaks the visual progress cue and the consistency of the wizard.

**Suggested fix:** Add the same 'Step 3/5 • Describe Task' titled header to task_input.go View() that the sibling screens render.

---

### [MINOR] 'q' quits the wizard instantly with no confirmation, discarding typed task/rules text

**Phase:** probe  
**Evidence:** captures/0001-0001-initial.txt  

On non-text steps (file selection, template, review) pressing 'q' calls tea.Quit immediately. The confirm-quit modal (m.confirmQuit) only triggers while generation/LLM-send is in progress (m.progress.Visible || m.llmSending). A user who has typed a task and rules, then lands back on review and presses 'q', loses all input with no prompt. (Note: inside the text-input steps 'q' correctly types a literal 'q' and quit is Ctrl+Q/Ctrl+C — that part is fine.)

**Suggested fix:** Gate the immediate tea.Quit behind the same confirmQuit modal whenever the user has entered task/rules text or selected files — not only during active generation. wizard.go handleKeyPress, 'q' case (~line 614).

---

### [MINOR] Copy-to-clipboard ('c') gives no on-screen feedback

**Phase:** probe  
**Evidence:** captures/0014-copy.txt  

After generation, pressing 'c' on the Review screen copies the generated context to the clipboard — verified: wl-paste returns the generated prompt ('## ROLE & PRIMARY GOAL ...'). But the TUI shows no toast, status change, or confirmation; the footer still reads 'c: Copy'. The user cannot tell the copy succeeded.

**Suggested fix:** Show a transient '✓ Copied to clipboard' status message (like the existing '✓ Context generated successfully!' line) after a successful copy.

---

### [MINOR] Fuzzy filter matches the full path → surprising, noisy results

**Phase:** stress  
**Evidence:** captures/0002-filter-applied.txt  

Typing 'READ' in the file filter and pressing Enter does not surface README.md near the top. Instead it auto-expands graphify-out/cache/ast/ and lists dozens of hex-named JSON files (e.g. 030442465dee...json). Those match because the fuzzy subsequence r-e-a-d is satisfied across the whole relative path (g[r]aphify / c[a]che ... d in the hash), not the filename. Result floods the tree with irrelevant cache files and buries the obvious intended match.

**Suggested fix:** Score matches against the file/dir basename (or weight basename hits far above path hits) and/or sort results by match score so README.md ranks first. Consider not auto-expanding deeply nested low-score directories.

---

### [COSMETIC] Size/progress bar stretches the full terminal width on wide terminals

**Phase:** visual  
**Evidence:** captures/0004-wide-160x40.txt  

At 160x40 the empty size bar (░ characters) spans the entire 160-column width, a very long mostly-empty bar for a 1.3% fill. Looks disproportionate on wide/tiled-WM terminals. Renders fine at 80x24 and 60x20.

**Suggested fix:** Cap the progress/size bar at a sensible max width (e.g. 60–80 cols) and left-align, rather than scaling it to full terminal width.
